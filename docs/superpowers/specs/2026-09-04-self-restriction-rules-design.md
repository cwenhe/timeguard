# 自控钟：每周指定时段应用限制设计规格

## 1. 背景与目标

用户需要在自己的 HarmonyOS 6 手机上实现“每周某些天、某段当天时间内，指定的应用（如同花顺、抖音）不能打开”，并且希望做成可配置、可自行安装使用的独立鸿蒙应用，而不是依赖系统“整机停用 + 白名单”的反向配置。

第一版只使用系统 Screen Time Guard Kit 原生支持的能力，不引入 A股交易日历、联网数据、后台日历调度器或跨天时间窗，目标是尽快形成可真机验收的最小版本。

## 2. 产品边界

### 2.1 纳入本版本

- 独立 ArkTS Stage 工程，包名固定为 `com.cwenhe.timeguard`，桌面显示名“自控钟”。
- 一条规则 = 一个或多个目标应用 + 一周内生效日（周一至周日任意组合）+ 当天开始/结束时间 + 启用开关。
- 每条规则由用户填写规则名（如“抖音和同花顺”“股票”），因为 Screen Time Guard 应用选择页只返回不透明 token，官方不提供 token 反查应用名的公开能力，自控钟页面无法展示应用名与图标。
- 支持新增、编辑、启用、停用、删除规则。
- 规则处于生效时段时锁定该规则的停用、删除与编辑，不提供紧急解锁入口；其他未生效规则不受影响。
- 策略启动/生效期间系统禁止卸载自控钟，避免通过卸载绕过限制（依赖鸿蒙 6.1.1(API 24) 起的授权应用配置）。
- 编辑规则时重新拉起系统应用选择页，并把原目标应用 token 全部作为预选项传入；用户在系统选择页内可看到真实应用名与图标。
- 规则卡片展示“限制 N 个应用”；系统选择页是查看真实应用名单的唯一入口。
- 规则写入本地并同步到 Screen Time Guard：禁止名单（BLOCKLIST）+ 周重复起止时间策略。
- 应用启动时查询系统策略，把界面开关校准到真实状态。
- 所有接口失败转成用户可理解的中文状态提示。

### 2.2 不在本版本范围

- 中国工作日、法定节假日、调休和 A股交易日历。
- 跨天时间窗（如 21:00 至次日 07:00）。
- 同一天多条时段、同一 App 多条规则。
- 联网日历数据源及离线兜底。
- 悬浮时钟。
- 分身应用、多用户空间、隐私空间适配。
- 后台定时刷新器：生效和结束完全交由 Screen Time Guard 的周重复策略执行。
- 阻止用户在“健康使用设备”中撤销屏幕时间守护授权；撤销入口由系统控制，应用无法覆盖。

## 3. 数据模型

### 3.1 限制规则（本地持久化）

```text
Rule {
  id: string              // 本地唯一标识，如 UUID
  name: string            // 用户输入的规则名，如“抖音”
  appTokens: string[]     // 系统应用选择页返回的不透明 token 列表，去重且不能为空
  weekdays: number[]      // 1=周一 … 7=周日，至少包含一天
  startTime: string       // HH:mm，24 小时制，如 "19:00"
  endTime: string         // HH:mm，24 小时制，如 "21:00"
  enabled: boolean        // 是否已同步并启动
}
```

约束：

- `weekdays` 元素必须属于 1 到 7，且不能为空。
- `startTime` 和 `endTime` 必须可解析为当天时间，且 `endTime` 晚于 `startTime`，不允许跨天。
- `appTokens` 不能为空，读取本地数据时自动过滤空串并去重。
- 旧版本保存的单 token 数据（`appToken` 字段）在读取时自动迁移为 `appTokens` 数组，不需要用户手动重建规则。
- 同一 App 第一版只允许出现在一条规则中；出现重复时由用户自行避免，本版本不实现查重提示。
- 规则名不能为空，长度不超过 30 个字符。

### 3.2 Screen Time Guard 策略

每条本地规则对应一个系统守护策略：

```text
GuardStrategy {
  name: "rule_" + rule.id
  timeStrategy: {
    type: START_END_TIME_TYPE,
    startTime: rule.startTime,
    endTime: rule.endTime,
    repeat: rule.weekdays
  }
  appInfo: { appTokens: rule.appTokens }
  appRestrictionType: BLOCKLIST_TYPE
}
```

## 4. 界面设计

### 4.1 主页面：规则列表

- 页面标题“自控钟”。
- 每个规则卡片显示：
  - 规则名；
  - 应用数量文本（“限制 N 个应用”）；
  - 生效日文本（“每天”“周一至周五”“周一、周三、周五”等）；
  - 时间窗文本（如 `19:00 – 21:00`）；
  - 启用开关；
  - 编辑入口、删除入口。
- 页面底部或右下角提供“添加规则”。
- 首次进入时尝试读取已授权的系统策略，校准所有开关状态。

### 4.2 新增/编辑规则页

字段与流程：

1. 规则名输入框（必填）。
2. 生效日选择：周一至周日复选，至少选一天。
3. 开始/结束时间：时间选择器；校验结束晚于开始。
4. “选择要限制的应用”：
   - 先调用 `guardService.requestUserAuth(context, { isSupportAppUninstall: false })` 请求系统授权，声明策略生效期间应用不可卸载；
   - 再调用 `appPicker.startAppPicker()` 拉起系统应用选择页；
   - 编辑已有规则时把原 `appTokens` 全部作为预选项传入，系统页会预勾选；
   - 系统选择页支持多选，返回选中应用的 token 数组；
   - 返回后自控钟显示“已选择 N 个应用（打开系统选择页可查看名单）”；保存时必须至少有一个 token。
5. 保存：
   - 本地写入/更新规则；
   - 若启用状态为开，则把规则同步为系统策略并启动；
   - 若保存前规则已停用，只更新本地，不启动系统策略。

### 4.3 启用/停用/删除

- 启用：本地规则置为启用，同步策略；若策略已存在则先停再更新，再启动。
- 停用：先解除名单中全部应用的禁止限制，再停止并移除对应系统策略，本地保留规则并置为停用。
- 删除：先解除名单中全部应用的禁止限制，再停止并移除系统策略，删除本地规则。
- 任一操作失败时回滚本地状态，并向用户展示具体失败原因。
- 生效判定：`enabled=true` 且当前星期命中、当前时间位于 `[startTime, endTime)`。
- 生效中的规则：卡片显示“限制生效中”，开关、编辑、删除入口不可用；停用/删除/保存操作执行前用最新系统时间再次校验，跨入生效区间后仍会拒绝。
- 保存一条“保存后立即生效”的规则或启用一条“当前时间已在其时段内”的规则时，先弹“规则将立即生效且本时段内不能解除”确认框，确认后才执行。
- 页面每 1 秒刷新一次当前时间，列表页与编辑页的锁定状态及时自动切换，避免时间边界处的按钮状态陈旧。
- 服务层 `deactivateRule` 同样按最新时间拒绝在规则时间窗内解除限制，作为界面拦截后的最后防线。

## 5. 系统能力接入

依赖能力：

- `@kit.ScreenTimeGuardKit` 的 `guardService` 与 `appPicker`。
- 权限：`ohos.permission.MANAGE_SCREEN_TIME_GUARD`，已在 AGC 申请通过，包名 `com.cwenhe.timeguard`。
- 工程需要用户本人在 DevEco 配置调试证书和包含该权限的 Profile；仓库不提交签名材料。

接口职责：

- `guardService.requestUserAuth(context, { isSupportAppUninstall: false })`：申请用户授权，并声明策略生效期间应用不可卸载；带应用配置的授权仅鸿蒙 6.1.1(API 24) 及以上支持。
- `appPicker.startAppPicker()`：安全拉起系统应用选择页，返回目标应用 token。
- `guardService.queryGuardStrategies()`：查询已存在策略，用于启动时校准开关。
- `guardService.addGuardStrategy()` / `updateGuardStrategy()`：创建/更新周重复策略。
- `guardService.startGuardStrategy()` / `stopGuardStrategy()`：启动/停止策略。
- `guardService.removeGuardStrategy()`：删除不再使用的策略。
- `guardService.releaseAppsRestriction()`：解除禁止名单（删除/停用前的兜底清理）。

## 6. 错误处理

| 错误码 | 含义 | 界面处理 |
| --- | --- | --- |
| 201 | 权限校验失败 | 提示检查 Profile/ACL 授权 |
| 401 | 参数错误 | 提示修正规则参数并保留用户输入 |
| 801 | 能力不支持 | 提示当前设备/系统版本不支持 |
| 1019000001 | 内部错误 | 展示错误并允许重试 |
| 1019000002 | 用户未授权 | 提示先完成系统授权 |
| 1019000003 | 用户取消 | 不改变现有状态 |
| 1019000004 | 策略数量超限 | 提示删除不用的规则后重试 |
| 1019000005 | 策略名已存在 | 内部先停再更新，仍失败则提示重试 |
| 1019000006 | 策略不存在 | 按本地状态重建策略 |
| 1019000007 | 策略执行中 | 先停止再更新 |
| 1019000008 | 策略未启动 | 直接启动 |

用户撤销授权或目标应用被卸载导致 token 失效时，界面显示中文说明，并允许用户重新授权或重新选择应用；本地规则在确认前不自动删除。

## 7. 验证矩阵

### 7.1 本地纯逻辑测试

- 规则名校验：空、超长。
- 星期数组校验：空、越界、去重、排序。
- 应用 token 数组校验：空数组拒绝、空串过滤、重复 token 去重、两组 token 顺序不同视为等价。
- 旧数据迁移：仅含 `appToken` 的旧规则读取后变为 `appTokens: [appToken]`，其余字段保持不变。
- 时间校验：格式错误、开始等于结束、结束早于开始、跨天拒绝。
- 生效判定：开始前一分钟不生效、开始时刻生效、结束前一分钟生效、结束时刻不生效、非命中星期不生效、已停用规则不生效但时间窗仍按计划命中。
- 生效日/时间窗文本格式化。
- 应用数量展示文案：0 个显示“尚未选择应用”，N 个显示“限制 N 个应用”。
- 本地规则持久化往返与启用状态恢复。

### 7.2 真机验收（DevEco + HarmonyOS 6 手机）

1. 首次点击“选择要限制的应用”：出现系统授权弹窗，拒绝/允许行为正确。
2. 授权后拉起应用选择页，勾选同花顺与抖音，返回后本地规则保存两个 token，列表显示“限制 2 个应用”。
3. 新建“同花顺和抖音：周一至周五 19:00–21:00 禁用”并启用。
4. 19:00 后点击同花顺、抖音均无法打开；若 19:00 时应用已在最前，期望被系统立即拦截/退出（平台行为以真机为准，不得静默降级）。
5. 21:00 后两个应用自动恢复可打开。
6. 该规则不影响其他应用；规则内少选一个应用后，另一个应用仍按同一时段被限制。
7. 新增第二条规则“快手：每天 22:00–23:00 禁用”，两条规则并存且互不影响。
8. 编辑规则：系统选择页同时预勾选原两个应用；取消勾选一个并新增一个后，策略更新为新的应用集合。
9. 停用规则后两个应用立即恢复；删除规则后本地与系统策略均清除。
10. 重启手机或 App 被清理后，已启用规则仍生效。
11. 用户在“健康使用设备/屏幕时间守护”中撤销授权后，App 显示明确状态，不误显示“运行中”。
12. 停用状态下保存编辑、删除后重启 App，界面状态与系统策略一致；单应用旧规则打开后自动迁移为数组格式且不丢失应用。
13. 规则进入生效时段后，列表页开关/编辑/删除被锁定，卡片显示“限制生效中”；尝试直接停用/删除被拒绝。
14. 编辑页停留在打开状态并跨入生效时段后，保存被拒绝并提示；退出时段后自动恢复可编辑。
15. 新增或启用一条“当前时刻已在其时段内”的规则时先弹确认框，确认后才生效并进入锁定。
16. 规则生效期间，其他未生效规则仍可正常新增、编辑、启停与删除。
17. 鸿蒙 6.1.1+ 设备完成带防卸载配置的授权并启用规则后，系统卸载入口不可用；停用或删除全部规则后恢复可卸载。

## 8. 风险与待真机确认项

- Screen Time Guard 周重复策略是否会在前台应用正在使用时主动退出该应用：规格期望为“到点立即不可继续使用”。若真机验证系统只阻止新的打开、允许已打开应用继续运行，暂停实现该验收项并先向用户确认后续方向，不静默降级。
- 同一 App token 在应用更新/重装后是否保持有效：以真机验证为准，失效时要求用户重新选择。
- AppConfig 防卸载配置不能热更新：升级安装后若此前授权未携带该配置，需先在“健康使用设备”撤销授权，再重新授权才会生效。
- 系统策略数量上限：本设计按最多几条规则规划，超限错误需原样呈现给用户。
- 生效期锁定的时间依据为手机本地时间；用户手动修改系统时间到时段外可绕过锁定，本版本不联网校时。
